## 2. 本轮已经完成的实际流程

`tools/run_nav_cycle.py`连接已有采集器与动态Page：

请求计划 → 官方HTTPS有限请求 → 保存原始响应与SHA256 → 严格解码 → 按原字段解析 → 重读原始证据并对账 → 独立交易日历完整性检查 → Node数据协议及精确计算检查 → 私人数据包与HTML预览构建。

默认dry-run，不联网、不落盘。执行必须指定新输出目录，保留前次证据；缺日、陈旧、错源、原始摘要不符或字段冲突均不得生成“合格预览”。源站请求1—4产品，本次两产品，超时/大小受限；不前填、不改写旧日期。

原始正文和净值不写入公共日志；公开诊断只有状态、数量、日期、摘要及非敏感结构。正式份额/资金仍缺失，不能由净值补造。

## 4. 实测问题和修复记录

首次工作流在创建job前因job级env不支持runner上下文而失败，已改为在shell步骤使用RUNNER_TEMP。之后真实运行器能访问源站，与当前工作容器的DNS失败不同。

实际排查确认两项解析问题：
1. 源站HTML声明GBK；原默认UTF-8解码失败。新增`nav_transport.py`，严格按HTTP/HTML/BOM声明解码；支持有声明的有界gzip，不使用替换字符掩盖问题，也未降低TLS检查。
2. 源站历史净值用`div.table / div.tr / div.td`构成，原解析器只识别原生table。新增结构解析，仍按“日期/单位净值”表头定位，累计净值和业绩增长率不能混入。

最终代码的首次run attempt遭遇URLError、没有取得响应；同一提交只重试一次后成功。错误根因尚不足以细分，因此不凭地域等信息断言源站封禁、持续故障或永久连通。失败历史保留于run attempt1，不掩盖稳定性问题。
